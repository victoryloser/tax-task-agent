# 执行与恢复协议

默认部署为单机SQLite；可选PostgreSQL保存共享业务库、队列、节点状态与回执，各主机只保留自己的本地checkpoint。无需Redis或Celery。

## 完整保存清单

所有请求先由同一真实模型生成request_manifest，再进入统一工具循环；清单解析也计入18次模型调用预算。保存请求持久化全部WriteTarget，包含票号、用途、备注、缺失字段、原用户引用及续办原turn。未要求修改的字段不列为缺项，缺票号目标也保留。

request_manifests与batch_items在首次写入前保存。模型明确整批原子要求时直接返回atomic_blocked，未调用任何发票写工具；只读用户返回denied。逐票执行按清单字段、原用户授权和当前版本检查，最终回执从全量清单生成，覆盖saved、failed、unverified、needs_input、not_executed等状态，不依赖模型自行列全结果。

跨会话上下文注入最近30个未完成目标；batch_status提供完整分页检索。续办通过previous_turn_id关联当前用户企业下的未完成票据，成功后旧目标标为superseded；已保存票据不会因“继续”而重复提交。batch_cancel经用户语义授权后取消未执行目标，作废其旧来源并递增epoch；保存的数据保留，待核实操作继续待核实。取消与工具回执同事务提交。

只读工具按turn＋工具名＋规范化参数记录尝试次数，默认首次调用后最多2次失败重试。显式企业与隐式当前企业使用同一预算键；换call_id、进程恢复不刷新预算。是否重试由模型决定，系统不自动循环重放业务写入。

## 提交与调度

Harness.submit在一个事务中创建真实用户消息、queued状态的turn和turn_jobs行。重复turn_id必须属于原会话且消息完全一致，否则报冲突。同步respond也先提交，再处理当前范围的队列直到目标turn完成；后台worker.run_once使用同一入口。

worker按入队顺序检查用户/企业范围，尝试取得该范围的非阻塞文件锁。忙碌范围跳过，其他范围继续执行；锁内重新选择最早queued/running轮次。未结束的旧轮次优先于后来请求。构建上下文时以当前turn为时间边界，排在后面的用户消息不会提前进入模型或授权判断。

文件锁由操作系统维护。杀进程会释放锁，不以“超过若干秒”判断旧worker失效，因此不会因模型调用慢而出现两个worker同时处理同一范围。进程监督器启动指定数量的子进程，异常退出会补位；整个监督服务退出后，队列仍保留，重启服务接续。

PostgreSQL模式用会话级advisory lock锁定用户/企业范围；取得锁时递增scope_fences.generation。范围内的每个业务事务先共享锁定并检查该代次，接管后的旧worker不能继续提交旧任务。权威状态在共享数据库，本地checkpoint丢失不导致重放已经提交的写入。网络中断不是“可以重写”的证据；未知结果仍只核实台账。

SQLite迁移由migrate-postgres执行，要求停止原库写入、目标库为空；单事务导入原rowid顺序、业务、队列和回执，重置序列。integration/test_postgres.py 覆盖 TCP 数据库连接、跨进程协调和本地 checkpoint 隔离。

## 持久节点状态

turn_jobs.state_json保存messages、effects、tool_count、epoch、answer及下一阶段phase。模型返回后先保存包含原tool_call ID的状态，再执行工具；工具节点结束后保存下一阶段。LangGraph负责模型/工具循环及其checkpoint，业务库中的节点状态与操作回执负责崩溃恢复。

| 中断位置 | 接续行为 |
|---|---|
| 用户入队后、模型调用前 | 从queued轮次开始，真实用户消息不重复插入 |
| 模型请求发送后、响应落库前 | 可能再次发送模型请求；已记录的调用计入原预算 |
| 模型响应落库后、工具开始前 | 沿用原工具名、参数与call_id |
| 发票事务提交后、查回前 | 按稳定请求号找到同事务台账，独立查回，不再修改发票 |
| 任务/偏好事务提交后、工具日志前 | 读取同事务data_json回执，不重复增删改，不额外增加revision/epoch |
| 工具结果落库后、节点快照前 | 复用tool_invocations.result_json，再完成节点快照 |
| 最终回复落库后、worker返回前 | turns与助手消息同事务完成，队列不再领取该turn |

同一个call_id重新出现时，名称与参数必须与登记值完全一致。工具执行记录和结果缓存同事务保存，恢复不会追加重复tool_execution。发票幂等还以turn＋票号绑定，避免模型另起调用ID重复保存。

恢复不会刷新调用预算，也不会隐去先前失败。未知或待核实写入状态继续阻止后续修改。记忆epoch变化时重新选择有效上下文，已执行操作仅注入不含旧偏好内容的简要回执。

## 长历史压缩与检索

模型保留最近10条消息；较早历史中的用户原话按当前请求的双字片段相关度和时间排序，最多选择8条，每条最多320字符，存入context_summaries。每条含真实message_id、原文quote及truncated标志；日志记录原始和压缩字节数。提取式压缩保留用户原话，便于根据消息 ID 追溯。

recall_history可按message_id或关键词子串分页读取完整用户原话，仅访问当前会话、当前用户/企业和有效epoch。压缩内容不替代当前金额、用途、规则、任务或授权；需要业务现状仍调用业务工具，写入仍引用本轮请求并走原消息授权。

更正/删除记忆时删除对应范围的压缩副本，旧epoch原话不参与下一轮检索。审计历史保留，不能因保留日志而重新注入被删除偏好。

HISTORY_MODE=semantic启用同一模型生成history_summary，逐条来源必须匹配所选用户原文。摘要按会话、epoch和历史边界缓存；失败显式返回，不换模型或静默降级。摘要只提供背景，不能作为当前业务数据或新写入授权。失效来源片段从批次和任务上下文引用中裁剪，同消息中的独立有效请求继续保留。

TOKENIZER_DIR指定本地HuggingFace tokenizer，TOKENIZER_MODEL必须匹配LLM_MODEL；apply_chat_template对实际消息、工具schema和生成提示计数，记录input_template_tokens并应用CONTEXT_TOKENS预算。只加载本地文件且不执行远程代码。Token 计数按本地模板计算，服务端模板或工具序列化方式变化时需同步配置。未配置时使用48,000字节预算。

## 服务启动与旧轮次核对

runtime.service按主机名限制同一主机的重复监督器，允许不同主机各自运行。Windows User模式在用户登录时通过隐藏启动项运行，Machine模式创建SYSTEM开机计划任务；Linux提供systemd单元。服务安装与数据库配置见 [配置与运行](development.md)，日志位于runs/service/worker.log。

recover-legacy识别没有turn_jobs的旧running轮次，默认预览，--apply保存核对回执。已提交发票根据操作台账独立查回；已记录工具结果保留；无法确定的旧修改列为未核实，不从缺失日志推断成功或自动重放。重复执行不会再次修改发票。

## 测试与边界

测试包括两个真实Python子进程竞争6条工作、提交发票后os._exit退出、监督器重启worker、任务/偏好事务完成后中断、删除后epoch变化、恢复预算不重置、排队未来消息隔离和网页后台提交/刷新。模拟Provider只用于这些可重复的故障测试；真实模型队列、提交中断恢复和长历史检索另行记录。

SQLite及PostgreSQL事务修改通过台账/回执获得可验证的单次生效语义，模型HTTP调用不保证单次发送；不承诺任意外部系统副作用的分布式exactly-once。同步模式进程中断后需worker继续消费，或者重新提交同一turn_id。无节点回执的旧记录提供核对工具，不能恢复从未记录的信息。
